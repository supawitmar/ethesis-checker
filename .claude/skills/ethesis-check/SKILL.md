# การตรวจรูปเล่มอิเล็กทรอนิกส์ (e-thesis checker)

ระบบตรวจ format รูปเล่มให้เจ้าหน้าที่บัณฑิตวิทยาลัย ม.มหิดล
FastAPI + pdfplumber + Jinja2 — **เครื่องมือช่วยเจ้าหน้าที่ ไม่ใช่ผู้ตัดสินแทน**

## แหล่งความจริง (อ่านก่อนตัดสินใจเรื่องกฎ)

**นโยบายการตรวจทั้งหมดอยู่ใน `RULES_AND_SOURCES.md`** — ลำดับอำนาจของแหล่งข้อมูล (§1),
ตารางกฎทั้งหมด (§2), ความขัดแย้งระหว่างเอกสารที่บันทึกไว้ (§5), ขั้นตอนบังคับเมื่อเพิ่มกฎ (§6),
กติกาการระบุตำแหน่งในรายงาน (§7) · ไฟล์นี้ไม่ทำซ้ำเนื้อหานั้น เพื่อไม่ให้แก้สองที่แล้วลืมข้างหนึ่ง

| อะไร | ที่ไหน |
|---|---|
| นโยบาย/ที่มาของกฎ (ต้นทางเดียว) | `RULES_AND_SOURCES.md` |
| ทะเบียนกฎที่ระบบใช้จริง | `ethesis_rules.py` (`RULE_CATALOG`) |
| เครื่องยนต์ตรวจ | `checker.py` (`run_check`) |
| กฎรายหน้า (หน้าไหนตรวจอะไรด้วยรหัสอะไร) | `reference/rules-by-page.md` |
| วิธีติดตั้ง/ด่านตรวจ/โครงสร้างไฟล์ | `README.md` |
| วิธี deploy + ความปลอดภัย | `DEPLOY.md` |

**เอกสารทางการ (อยู่นอก repo — คนละเครื่องอาจวางไว้คนละที่)**
ประกาศบัณฑิตวิทยาลัย 2569, คู่มือการจัดรูปแบบ, และ template `.docx` ทางการ
ถ้าหาไม่เจอในเครื่องให้ถามเจ้าของโปรเจกต์ **ห้ามเดารูปแบบเอง** — เปิด template ที่ตรง
ประเภท/ภาษา/รูปแบบมาดูก่อนเขียนกฎเสมอ (เคยพลาดมาแล้วเรื่อง format รายชื่อกรรมการ
บนหน้าบทคัดย่อ)

## หลักการตัดสินสี

| สี | หมายถึง | ใช้เมื่อ |
|---|---|---|
| 🔴 RED | ไม่ผ่าน | ผิดชัดเจน ระบบยืนยันได้เอง (รวม typo — เจ้าหน้าที่ตรวจอย่างเข้ม) |
| 🟠 ORANGE | รอยืนยัน | ระบบไม่มั่นใจ / ต่างเฉพาะวรรคตอน / อ่านจาก PDF ไม่ได้ |
| 🟡 YELLOW | ผ่านได้ | เป็นข้อสังเกต เช่น ตัวหนาในบทคัดย่อ หน้าว่างที่เลขหน้ายังถูก |

`Report.verdict()`: มี RED → `ไม่ผ่าน` · มี ORANGE → `รอยืนยัน` · นอกนั้น `ผ่าน`

**หลักการที่ห้ามละเมิด**

1. **ห้ามฟันธงสิ่งที่ยืนยันไม่ได้** — อ่าน PDF ไม่ออก/ข้อมูลไม่พอ = ส้ม ไม่ใช่แดง
   รวมถึง "ระบบอ่านผิด" ด้วย: การอ่านที่เพี้ยนต้องไม่กลายเป็นคำตัดสินว่าเล่มไม่ผ่าน
2. **ห้ามให้ AI ตัดสินผ่าน/ไม่ผ่านเอง** ยกเว้นที่เจ้าหน้าที่อนุมัติไว้แล้ว
3. **ทุกข้อที่แสดงต้องมี** ตำแหน่ง / สิ่งที่พบ / สิ่งที่ควรเป็น / วิธีแก้ / รหัสกฎ
4. **ไม่ฟ้องเลื่อนทั้งแถว** — ของที่เป็นชุด (รายชื่อกรรมการ) ให้เทียบแบบ set-diff
   แล้วบอกอาการจริง (ขาด/เกิน) ไม่ใช่ฟ้องทุกช่องที่เลื่อน
5. **ข้อที่ไม่ใช่ความผิดของเล่ม ต้องตั้ง `system_note=True`** เพื่อไม่ให้ไปอยู่ใน
   "จุดที่นักศึกษาต้องแก้" (เช่น ช่องฟอร์มว่าง, ระบบอ่านหน้าไม่ออก)

## เพิ่มหรือแก้กฎ — ทำตามลำดับนี้

1. หาที่มาจากประกาศ/คู่มือ/template ก่อน ถ้าไม่มีข้อกำหนดทางการ ให้ติดป้ายว่า
   **"กติกาปฏิบัติงาน"** ห้ามเขียนว่าเป็นข้อกำหนดในประกาศฯ
2. ใช้รหัสกฎที่มีอยู่ หรือสร้างใหม่ใน `RULE_CATALOG` (ต้องมี title/basis/references)
3. เขียนโค้ดใน `checker.py` — แยกเป็นฟังก์ชัน `_report_*(rep, ...)` เพื่อให้เทสได้
   โดยไม่ต้องเปิด PDF จริง (unittest ทั้งชุดต้องรันจบใน ~1 วินาที ห้ามพา PDF เข้าไป)
4. `rep.add(zone, part, loc, found, expected, fix, rule_id)` — ใส่ `rule_id` เสมอ
5. เพิ่ม unittest **อย่างน้อย 1 กรณีผ่าน + 1 กรณีไม่ผ่าน**
6. เพิ่มคำแปลอังกฤษของข้อความใหม่ใน `templates/report.html` (array `TR`)
7. อัปเดต `RULES_AND_SOURCES.md` (ตาราง §2 และหัวข้อรายละเอียดที่เกี่ยว)
8. ยืนยันผล (ด้านล่าง) แล้วค่อย commit

## การยืนยันผล (ทำครบทุกข้อก่อน commit)

รันจากโฟลเดอร์ `code/` — รายละเอียดและตารางว่าด่านไหนต้องมีข้อมูลทดสอบบ้าง
อยู่ในหัวข้อ "ทดสอบ" ของ `README.md`

```bash
python -m unittest discover -s tests
```

```bash
python tools/regress_books.py
```

```bash
python tools/check_i18n.py --lint
```

```bash
python tools/check_i18n.py --corpus
```

```bash
python tools/smoke_web.py
```

- **regression เปลี่ยนตัวเลข** ต้อง**อธิบายได้ว่าทำไม** ถ้าอธิบายไม่ได้ = ยังไม่เสร็จ
  ห้าม commit · ถ้าเป็นการเปลี่ยนที่ตั้งใจ ให้บันทึกฐานใหม่ด้วย `--save`
- **positive test**: กฎใหม่ต้องพิสูจน์ว่า "ฟ้องจริง" ด้วย — เล่มทดสอบส่วนใหญ่สะอาด
  การไม่มี finding จึงพิสูจน์อะไรไม่ได้
- **`--lint` ต้องได้ 0 ทุกบรรทัด** โดยเฉพาะ `entry ที่แยกไม่ออก` — คำแปลที่คร่อมด้วย
  `'...'` แล้วมี apostrophe ข้างใน (`the student's name`) จะทำให้ JS ปิดสตริงตรงนั้น
  แล้ว `<script>` **พังทั้งบล็อกแบบเงียบ ๆ** ไม่มี error ในหน้าเว็บ รู้อีกทีคือปุ่มสลับ
  ภาษาไม่ทำงาน — ถ้าคำแปลมี apostrophe ให้คร่อมด้วย `"..."` แทน
- **i18n ต้องได้ `UNTRANSLATED: 0`** และ **ตัวเลข "ยังพึ่งเศษคำ" ห้ามเพิ่มขึ้น**
  (`--corpus` พิมพ์ให้ดูทุกครั้ง) — ดูวิธีเขียนกฎด้านล่าง
- **ตรวจบนเบราว์เซอร์จริงด้วย** เมื่อแก้ `report.html` — เปิดหน้ารายงาน สลับภาษา
  แล้วดูว่าไม่มี console error (dev server: `.claude/launch.json` ชื่อ `ethesis`)

## เขียนคำแปลอังกฤษ (`TR` ใน report.html)

ตัวแปลทำงาน **2 ชั้น** (`trWhole` แล้วค่อย `trEN`) — เขียนกฎให้เข้าชั้น 1 เสมอ

| ชั้น | ทำอะไร | ลำดับกฎมีผลไหม |
|---|---|---|
| 1 กฎเต็มประโยค | หากฎที่กิน **ทั้งสตริง** เจอแล้วใช้ทันทีและหยุด | **ไม่มีผล** ปลอดภัย |
| 2 เศษคำ | แทนที่สะสมทีละกฎ ใช้เมื่อชั้น 1 ไม่แมตช์ | **มีผล** เปราะ |

- **เขียนกฎให้กินทั้งประโยค** โดยผูกค่าที่แปรผันเป็นวงเล็บจับ เช่น
  `[/ชื่อเรื่องในเล่มเขียนว่า ("[^"]*")/g, 'The thesis title in the document reads $1']`
- **ค่าที่จับได้จะถูกแปลต่อ** ด้วยกฎเต็มประโยคของมันเอง (เรียกซ้ำ) **ยกเว้น**ค่าที่
  คร่อมด้วยเครื่องหมายคำพูดทั้งก้อน ซึ่งถือเป็น "ค่าที่อ่านได้จากเล่ม" คงเป็นไทยเสมอ
  → **ค่าจากเล่มต้องอยู่ในเครื่องหมายคำพูดเสมอ** ตอนสร้างข้อความใน `checker.py`
- **คำสั้น ๆ ที่ห้ามยิงกลางประโยค** ให้เขียนผูกหัวท้าย เช่น `[/^ชื่อบท$/g, ...]`
  แบบนี้ชั้น 2 จะแตะไม่ได้เลย ใช้ได้เฉพาะตอนเป็นค่าที่จับมาจากกฎเต็มประโยค
- ถ้าจำเป็นต้องเพิ่มกฎเศษคำ ให้วางไว้ **ล่างสุด** และรู้ตัวว่ามันฉีกประโยคที่ยังไม่มี
  กฎเต็มได้ · ตัวเลข "ยังพึ่งเศษคำ" จาก `--corpus` คือหนี้ที่ต้องลด ห้ามเพิ่ม

## ข้อควรระวังเฉพาะโปรเจกต์

- **git root คือโฟลเดอร์ `code/`** ไม่ใช่โฟลเดอร์แม่
- **ห้าม push** — commit ในเครื่องเท่านั้น เจ้าของอัปโหลดขึ้น GitHub เอง
  รายงานจำนวน commit ที่ค้างทุกครั้ง: `git rev-list --count '@{u}..HEAD'`
- **commit message ภาษาไทยยาว ๆ ให้ใช้ `git commit -F <file>`** — PowerShell 5.1
  แยกอาร์กิวเมนต์ผิดเมื่อ here-string มีเครื่องหมายคำพูดข้างใน
- **ข้อความไทยจาก PDF เพี้ยนเสมอ** — สระ/วรรณยุกต์เรียงผิด, มี PUA (`U+F700`+),
  นิคหิตของ `ำ` ถูก map เป็นช่องว่างกว้างศูนย์, mark หลุดออกมาเป็นคำของตัวเอง
  → เทียบภาษาไทยต้องผ่าน `norm()` เสมอ และอ่านข้อความหน้าผ่าน `_page_text()`
  ไม่ใช่ `page.extract_text()` ตรง ๆ
- **ไม่มี `ANTHROPIC_API_KEY` ในเครื่อง** → `llm_assist.translate_names()` คืน `[]`
  เล่มอังกฤษจึงตกไปทาง ORANGE เวลาทดสอบในเครื่อง **เป็นพฤติกรรมที่ถูกต้อง ไม่ใช่บั๊ก**
- **หัวเรื่องอ่านจากบรรทัดบนสุดของหน้าเท่านั้น** (`top_lines`) ไม่สแกนทั้งหน้า
- **หน้าลงนามเป็นตารางตายตัว** 2 คอลัมน์ × 8 แถว เหมือนกันทุกหลักสูตร/ประเภทเล่ม
  กรรมการเติมขวาบน→ล่าง (1–5) แล้วซ้ายล่าง→บน (6–9) — แต่**ระบบไม่ตัดสินจากตำแหน่ง**
  ดูแค่ว่าชื่อครบและถูกคน เพราะแต่ละเล่มจัดหน้าไม่เหมือนกัน
- **รหัสผ่านเข้าใช้งานอยู่ใน `.env`** (ไฟล์นี้ถูก gitignore) — ห้ามเขียนค่าจริงลงเอกสาร
  หรือ commit ขึ้น git เด็ดขาด เช่นเดียวกับ `ANTHROPIC_API_KEY`
